Arkhos

Centro de mando personal modular. Una plataforma privada que unifica la gestión de proyectos, mercados financieros, patrimonio y gastos en un solo lugar — construida con un nivel de ingeniería que va mucho más allá de lo convencional.

¿Por qué existe Arkhos?

Imagina que llevas tus proyectos de trabajo en Notion, tus inversiones en un Excel, los gastos del mes en una app del banco, y los precios de mercado los consultas en cinco pestañas distintas del navegador. Cada herramienta tiene su suscripción, sus datos están en silos separados, y ninguna está diseñada para ti específicamente.

Arkhos resuelve este problema construyendo una plataforma donde todos estos módulos conviven bajo un mismo techo, con tus datos almacenados de forma privada en tu propia base de datos, sin depender de servicios externos que puedan desaparecer o cambiar sus precios.

El nombre

ἀρχός (arkhós) es una palabra del griego antiguo que significa "el que lidera", "el que está al origen", "el que manda". Es la raíz etimológica de palabras que usamos a diario: arquitectura (el que diseña la estructura), arconte (el que gobierna), monarquía (gobierno de uno). El nombre no es casual: refleja la filosofía central de la plataforma — tú estás al mando de tus datos, tus proyectos, tus finanzas.

Para quién es

Personas técnicas o semi-técnicas que quieren un único lugar privado, sin suscripciones por módulo, diseñado específicamente para una sola persona en lugar de intentar ser universal. Arkhos no es un SaaS multi-tenant — es una plataforma personal, construida con los mismos estándares de ingeniería que usarías para un producto con miles de usuarios, pero al servicio de uno solo.

Sección 02

Stack tecnológico

Cada tecnología fue elegida con un criterio claro: resuelve un problema real del proyecto, tiene adopción estable, y encaja con el resto sin fricciones. No hay ninguna dependencia "porque es popular" — cada una gana su lugar en el stack.

Framework web

Next.js 16

Next.js es un framework construido sobre React que permite crear aplicaciones web completas. Lo que lo hace especial es que puede ejecutar código tanto en el navegador del usuario (lo que ve) como en el servidor (la lógica interna). Esto significa que una sola herramienta maneja tanto la interfaz visual como la conexión con la base de datos, la autenticación y la lógica de negocio.

La versión 16 trae el "App Router", un sistema que organiza las páginas de la aplicación en carpetas. Cada carpeta dentro de src/app/ se convierte automáticamente en una ruta web: la carpeta proyectos genera la página /proyectos.

Lenguaje

TypeScript (modo strict)

TypeScript es JavaScript con un sistema de tipos. Piénsalo como una capa de seguridad: cada variable, cada función, cada dato que entra o sale tiene que declarar qué tipo de información contiene. Si una función espera un número y alguien le pasa un texto, TypeScript lo detecta antes de que el código se ejecute.

El "modo strict" es la configuración más exigente posible. Arkhos tiene 0 errores de TypeScript y 0 usos de any (la válvula de escape que desactiva los tipos). Esto significa que cada pieza de código está verificada por el compilador.

Estilos visuales

Tailwind CSS v4

Tailwind es un sistema de clases CSS que permite diseñar directamente en el HTML. En lugar de escribir archivos CSS separados con nombres inventados (.boton-grande-azul), usas clases atómicas que describen exactamente lo que hacen: px-4 (padding horizontal 16px), bg-accent (fondo terracota), rounded-xl (bordes redondeados 12px).

La versión 4 permite definir variables CSS del brand en un archivo central (globals.css) y usarlas en toda la app sin repetir valores hex manuales. Los colores, tipografías y espaciados de Arkhos están definidos una sola vez.

Base de datos y autenticación

Supabase

Supabase es una plataforma que agrupa cuatro servicios en uno: autenticación de usuarios (login, registro, MFA), base de datos PostgreSQL, almacenamiento de archivos (para logos de proyectos) y seguridad a nivel de fila (cada usuario solo ve sus propios datos, incluso si alguien accediera directamente a la base de datos).

La ventaja principal: tus datos están en tu propia instancia de PostgreSQL, no mezclados con los de otros usuarios en un servidor compartido. Tienes control total sobre tus datos.

Estado global

Zustand

Cuando varios componentes de la interfaz necesitan acceder a la misma información (por ejemplo, la lista de proyectos aparece tanto en la vista lista como en el kanban), esa información se guarda en un "store" central. Zustand es la librería que gestiona estos stores.

Lo especial de Zustand en Arkhos es que implementa "optimistic updates": cuando creas un proyecto, la interfaz se actualiza inmediatamente (sin esperar a que el servidor responda). Si el servidor falla, el cambio se revierte automáticamente.

Validación de datos

Zod v4

Zod es una librería que valida que los datos tengan la forma correcta antes de usarlos. Cuando un usuario rellena un formulario para crear un proyecto, Zod verifica que el nombre no esté vacío, que el stack sea un array de strings, que la fecha tenga el formato correcto. Esta validación ocurre tanto en el navegador (feedback inmediato) como en el servidor (protección contra manipulación).

Iconos

Lucide React

Lucide es una biblioteca de iconos SVG line-style (trazos finos y limpios). Arkhos usa 76 de estos iconos solo en el selector de iconos de proyectos, más los iconos de navegación, acciones y estados. La regla del design system es clara: nunca emojis en la interfaz, siempre iconos Lucide con stroke de 1.5-2px.

Drag & drop

@dnd-kit

@dnd-kit es el motor que permite arrastrar y soltar fases y tareas para reordenarlas. A diferencia de otras librerías, @dnd-kit fue diseñada desde cero para ser accesible (funciona con teclado, no solo ratón) y se integra bien con React sin conflictos de renderizado.

En móvil, donde arrastrar es incómodo, el sistema cambia automáticamente a botones de flecha arriba/abajo.

Testing

Vitest + Testing Library

Vitest ejecuta los 34 tests automáticos del proyecto. Cada test verifica un comportamiento específico: "si un usuario no está autenticado, debe redirigir a login", "si el nombre del proyecto está vacío, la validación debe fallar", "formatCurrency(1234.5, 'EUR') debe devolver '1.234,50 €'".

Testing Library permite testear componentes React tal como los usaría un usuario real: buscando elementos por texto visible, no por IDs internos.

Gestor de paquetes

pnpm

pnpm (performant npm) es el gestor de paquetes que instala las dependencias del proyecto. Es hasta 2x más rápido que npm porque almacena los paquetes en una caché global y crea enlaces simbólicos en lugar de copiar archivos. En Arkhos, la instalación completa de dependencias tarda menos de 10 segundos.

Decisiones técnicas clave

¿Por qué Next.js y no Vite + React Router? Next.js ofrece Server Components nativos (renderiza HTML en el servidor, reduce JavaScript enviado al navegador), Server Actions (funciones que se ejecutan en el servidor sin API routes manuales), y un sistema de middleware (proxy.ts) que intercepta todas las requests para validar autenticación. Con Vite, todo esto habría que implementarlo manualmente.

¿Por qué Zustand y no Redux o Context? Zustand es 2KB comprimido (Redux Toolkit es ~30KB). No requiere Providers envolventes. Un store es una función de una línea: const useStore = create((set) => ({...})). Para una app personal modular donde cada módulo tiene su propio store, esta simplicidad importa.

¿Por qué Supabase y no Firebase o Prisma + Postgres? Supabase agrupa auth + DB + storage + RLS en un solo servicio. El dato clave: Row Level Security está implementado a nivel de PostgreSQL, no a nivel de aplicación. Esto significa que la seguridad funciona incluso si se accede a la base de datos directamente saltándose la app.

Sección 03

Cómo está construido

Arkhos sigue una arquitectura modular con App Router de Next.js. Cada módulo tiene su propio espacio en la estructura de carpetas, su store de Zustand y sus componentes, pero todos comparten la misma shell de navegación, component library y sistema de autenticación.

¿Qué pasa cuando abres Arkhos?

Cuando escribes arkhos.pelayodelafuente.es/proyectos en tu navegador, se desencadena una secuencia precisa de 7 pasos que garantiza que solo tú puedes ver tus datos. Vamos a recorrer cada uno:

Flujo de una petición protegida: del navegador a la base de datos y de vuelta

Paso 1 — Tu navegador envía la petición a la red global de servidores de Vercel (Edge Network). El servidor más cercano a ti geográficamente recibe la request.

Paso 2 — proxy.ts (Middleware) intercepta la petición antes de que llegue a la página. Crea un cliente de Supabase, lee las cookies de sesión del navegador y llama a getUser() para verificar que eres un usuario autenticado. Si no lo eres, te redirige a /login. Si tienes MFA activado pero no has verificado el segundo factor, te redirige a /verify-mfa.

Paso 3 — App Router ejecuta el Server Component de la página. Este código se ejecuta en el servidor (no en tu navegador), obtiene tu userId y renderiza el esqueleto de la página con el componente ProjectsView.

Paso 4 — ProjectsView (Client Component) ya corre en tu navegador. Llama al store de Zustand para cargar los proyectos.

Paso 5 — Zustand Store llama al data layer (projects.ts) que ejecuta queries contra Supabase usando el SDK.

Pasos 6-7 — Supabase + PostgreSQL ejecuta la consulta SQL, pero antes de devolver resultados, PostgreSQL aplica las políticas de Row Level Security. Cada fila tiene una verificación: WHERE user_id = auth.uid(). Solo tus proyectos se devuelven, nunca los de otra persona.

¿Y cuando creas algo nuevo?

El flujo de creación (mutación) es igual de interesante porque usa "optimistic updates":

1. Pulsas "Crear proyecto" y rellenas el formulario.

2. El store aplica el cambio inmediatamente en la interfaz — el proyecto aparece al instante, sin esperar.

3. En paralelo, envía la petición de INSERT a Supabase.

4a. Si Supabase confirma: todo bien, el proyecto ya estaba visible.

4b. Si Supabase falla: el store revierte el cambio automáticamente y muestra un Toast de error. La interfaz nunca queda en un estado inconsistente.

Route groups y la separación auth/dashboard

Next.js App Router usa "route groups" (carpetas entre paréntesis) para compartir layouts sin afectar la URL. (auth) agrupa las rutas de autenticación que no muestran sidebar. (dashboard) agrupa las rutas protegidas que comparten sidebar, topbar y bottom nav. La URL final es limpia: /login, no /auth/login.

Server Components vs Client Components

Next.js distingue entre componentes que se ejecutan en el servidor (Server Components, por defecto) y los que necesitan interactividad del navegador (Client Components, marcados con 'use client'). En Arkhos, los Server Components se usan para obtener datos del usuario y renderizar la estructura de la página. Los Client Components se usan para la interactividad: formularios, modales, drag & drop, búsqueda en tiempo real.

Esta separación reduce el JavaScript enviado al navegador: el código del Server Component nunca llega al browser, solo su HTML resultante.

Sección 04

Base de datos

PostgreSQL en Supabase, con Row Level Security activo en las 8 tablas. La estructura es jerárquica, cuidadosamente diseñada para que cada relación tenga sentido y cada eliminación sea limpia.

Cómo se organizan tus datos

Piensa en la base de datos como un archivador con cajones organizados. Cada cajón es una "tabla" que guarda un tipo de información. Las tablas están conectadas entre sí de forma lógica:

8 tablas · Cada flecha 1:N significa "uno a muchos" (un proyecto tiene muchas fases)

La analogía del archivador

Tu cuenta (profiles) es la cerradura del archivador. Solo tú tienes la llave.

Dentro del archivador tienes carpetas de proyectos. Cada carpeta tiene separadores (las fases: "Diseño", "Desarrollo", "Testing"). Detrás de cada separador hay fichas (las tareas: "Implementar login", "Crear base de datos"). Y cada ficha puede tener post-its con URLs (los links: documentación, diseños en Figma, PRs de GitHub).

Si eliminas una carpeta de proyecto, todos sus separadores, fichas y post-its se eliminan automáticamente. Nunca quedan fichas huérfanas flotando sin proyecto.

Tipos y estados personalizables

Las categorías de los proyectos no están grabadas en piedra. Cada usuario puede crear sus propios tipos ("Web", "API", "CLI", "Side Project", "Investigación") y sus propios estados ("Idea", "Activo", "Pausado", "Completado"), cada uno con su color e icono. Esto significa que Arkhos se adapta a cómo tú organizas tu trabajo, no al revés.

Migrations

¿Qué es una migration?

Una migration es un archivo SQL numerado que modifica la estructura de la base de datos de forma controlada. Cada migration tiene un número de versión (001, 002, 003) y se ejecuta en orden. Esto permite evolucionar el schema de forma predecible y reproducible.

Sección 05

Autenticación y seguridad

Ocho capas de protección entre el mundo exterior y tus datos. La seguridad no es un añadido posterior — es parte fundamental de la arquitectura desde el día uno.

Las 8 capas de seguridad

Imagina tu información como un tesoro en el centro de una fortaleza con 8 muros concéntricos. Cada muro protege contra un tipo de amenaza distinto. Si un atacante consigue atravesar un muro, el siguiente sigue protegiendo.

01
HTTPS (cifrado del tráfico)
Vercel + Let's Encrypt · certificado automático
Todo lo que viaja entre tu navegador y el servidor está cifrado. Aunque alguien interceptara tu conexión WiFi, solo vería datos ilegibles. El certificado SSL se renueva automáticamente — Vercel se encarga de esto sin intervención manual.
02
Supabase Auth (identidad con JWT)
email/password · tokens JWT con rotación automática
Cuando introduces tu email y contraseña, Supabase verifica las credenciales y genera dos tokens: un "access token" (válido 1 hora) y un "refresh token" (válido 7 días). El access token es como un pase temporal que el navegador presenta en cada petición. Cuando expira, el refresh token obtiene uno nuevo silenciosamente, sin que tengas que volver a hacer login.
03
Middleware proxy.ts
Next.js Middleware · intercepta cada request
Antes de que cualquier página protegida se cargue, el middleware intercepta la petición y verifica que tienes una sesión válida. Si no la tienes, te redirige a la página de login. Si la tienes pero tu token necesita refrescarse, lo hace automáticamente. Es como el guardia de seguridad que revisa tu credencial antes de dejarte pasar.
04
MFA TOTP (segundo factor)
Google Authenticator / Authy · código de 6 dígitos
MFA (Multi-Factor Authentication) añade una segunda cerradura. Aunque alguien descubra tu contraseña, necesita además el código temporal de 6 dígitos que cambia cada 30 segundos en tu teléfono. TOTP (Time-based One-Time Password) es el estándar que usan Google, Microsoft y la mayoría de servicios profesionales. Lo configuras escaneando un código QR desde una app como Google Authenticator.
05
Row Level Security (RLS)
PostgreSQL · políticas por tabla en Supabase
Esta es la capa más profunda y potente. Cada fila de la base de datos tiene un "candado" implementado a nivel del motor de base de datos, no a nivel de la aplicación. Incluso si alguien consiguiera acceso directo a PostgreSQL saltándose completamente la app, solo vería sus propios datos. Es como si cada fila supiera quién es su dueño y rechazara cualquier otra solicitud.
06
Validación Zod (doble verificación)
Schemas idénticos en navegador Y servidor
Cuando envías datos (crear proyecto, editar tarea), se validan dos veces: primero en tu navegador (para darte feedback inmediato) y otra vez en el servidor (para proteger contra manipulación). Si alguien modifica el JavaScript del navegador para saltarse la validación del lado del cliente, el servidor bloqueará los datos inválidos igualmente.
07
Server Actions (lógica oculta)
Next.js Server Actions · código nunca expuesto al browser
Las operaciones sensibles (crear, editar, eliminar) se ejecutan en el servidor mediante "Server Actions". El código de estas funciones nunca se envía al navegador del usuario. Un atacante no puede inspeccionar la lógica de negocio ni encontrar formas de explotarla, porque simplemente no tiene acceso a ella.
08
Variables de entorno
.env.local + Vercel Dashboard
Las claves secretas (API keys, tokens de Supabase, credenciales de servicios) nunca aparecen en el código fuente. Están almacenadas en el Dashboard de Vercel y se inyectan al servidor en tiempo de ejecución. Incluso si alguien tuviera acceso al repositorio de GitHub, no encontraría ninguna credencial.

¿Cómo funciona el login?

El proceso de login puede parecer instantáneo desde fuera, pero por dentro ocurre una coreografía precisa:

1. Escribes tu email y contraseña en el formulario de /login.

2. Al pulsar "Entrar", un Server Action envía las credenciales directamente al servidor (nunca se exponen en una API pública).

3. Supabase Auth verifica las credenciales contra la base de datos de usuarios.

Si son incorrectas: se muestra un mensaje de error en el formulario. Sin revelar si el email existe o no (protección contra enumeración de usuarios).

Si son correctas: Supabase genera los tokens JWT y los escribe como cookies en tu navegador.

4. Redirige al dashboard (/). El middleware proxy.ts lee las cookies, verifica que el usuario es válido.

5. Si tienes MFA activado: el middleware detecta que tu nivel de seguridad es AAL1 (solo contraseña) pero necesitas AAL2 (contraseña + TOTP). Te redirige a /verify-mfa donde introduces el código de 6 dígitos de tu app de autenticación.

6. Código correcto → sesión asciende a AAL2 → acceso completo al dashboard.

🔐

AAL1 vs AAL2: AAL significa "Authentication Assurance Level". AAL1 = has demostrado quién eres con contraseña. AAL2 = has demostrado quién eres con contraseña + un dispositivo físico (tu teléfono). Es el mismo concepto que usan los bancos cuando te piden un SMS además de tu pin.

Sección 08

Stack Cognitivo

Arkhos no solo es una aplicación — tiene una infraestructura completa de desarrollo asistido por IA que hace que construirla sea sistemático, reproducible y robusto. Esta infraestructura es tan sofisticada como la propia app.

¿Por qué existe?

Desarrollar una aplicación con inteligencia artificial como asistente (Claude Code) presenta tres problemas serios que cualquier desarrollador reconocerá:

Problema 1

Amnesia entre sesiones

Claude no recuerda lo que hicisteis ayer. Cada sesión empieza desde cero: "¿qué versiones uso? ¿qué convenciones tenemos? ¿dónde nos quedamos?". Los primeros 15-20 minutos de cada sesión se desperdician reconstruyendo contexto.

Solución → Engram

Problema 2

Sobrecarga de contexto

Cargar todo el código del proyecto en cada conversación consume tokens (el "espacio de memoria" de la IA), limita el espacio para trabajo real y satura el contexto con información irrelevante para la tarea concreta del momento.

Solución → Skills + Context7

Problema 3

Sin red de seguridad

Código sin tests ni integración continua puede romperse silenciosamente. Un cambio aparentemente inocente puede romper el build en producción sin que nadie lo detecte hasta que un usuario lo reporta.

Solución → CI/CD + Vitest

Las 6 herramientas del Stack Cognitivo

🧠 Engram — Memoria persistente

Engram es una base de datos SQLite local que guarda "memorias" de desarrollo. Cada vez que se toma una decisión importante, se resuelve un bug, o se establece un patrón, se guarda una memoria con 4 campos: What (qué se hizo), Why (por qué), Where (archivos afectados), Learned (lecciones aprendidas).

Al inicio de cada nueva sesión de trabajo, se ejecuta mem_context project:"arkhos" y Claude recibe todas las memorias del proyecto. 18 memorias guardadas que dan contexto preciso sin tener que releer todo el código.

¿Por qué sobrevive a reinicios? Porque vive en disco (~/.engram/engram.db), no en la conversación. Cuando la IA "olvida" su contexto de conversación, las memorias persisten.

📋 CLAUDE.md — System prompt del proyecto

Un archivo de ~260 líneas que se carga automáticamente al inicio de cada sesión de Claude Code. Contiene todo lo que la IA necesita saber: stack con versiones exactas, estructura de carpetas, convenciones de código (commits, TypeScript, CSS, imports), paleta de colores, tipografías, inventario de componentes con sus props, puntos clave de seguridad, y protocolos de trabajo.

¿Por qué no más largo? Cada línea consume tokens del contexto de la IA. 260 líneas es el punto óptimo entre "suficiente información" y "no desperdiciar espacio para trabajo real".

📚 Skills — Conocimiento bajo demanda

En lugar de cargar toda la documentación en cada conversación, los Skills son archivos Markdown especializados que se cargan solo cuando son necesarios. Arkhos tiene 2 skills: supabase/SKILL.md (se carga cuando se trabaja con la base de datos o autenticación) y ui/SKILL.md (se carga cuando se crean o modifican componentes visuales).

Es como un médico que consulta un manual especializado solo cuando trata una enfermedad específica, en lugar de llevar encima toda la enciclopedia médica.

🔧 SDD — Spec-Driven Development (9 sub-agentes)

Para features grandes (más de 50 líneas de código), el desarrollo sigue un protocolo formal: documentar qué se va a hacer antes de escribir código. Claude Code actúa como orquestador y delega a 8 sub-agentes especializados, cada uno experto en una fase:

Explorer (analiza el código existente) → Proposer (propone solución) → Spec Writer (documenta requisitos) → Designer (define arquitectura) → Task Planner (divide en tareas) → Applier (implementa) → Verifier (verifica) → Archiver (archiva el resultado).

En puntos clave del pipeline hay "Human Gates" donde el trabajo se pausa y el humano debe aprobar antes de continuar. Esto evita que la IA avance en una dirección incorrecta.

📖 Context7 — Documentación actualizada de librerías

Context7 es un servidor MCP (Model Context Protocol) que provee documentación actualizada directamente en el contexto de Claude. Cuando la IA necesita saber cómo usar una API de @supabase/ssr v0.9.0, Context7 busca la documentación oficial actual en lugar de depender del conocimiento de entrenamiento (que puede estar desactualizado).

¿Por qué importa? Las librerías cambian sus APIs constantemente. Sin Context7, Claude podría usar parámetros que existían en la versión anterior pero ya no funcionan.

Sección 09

CI/CD y Testing

Tres workflows de GitHub Actions forman una red de seguridad automática que garantiza que ningún código roto llega a producción. Cada push, cada PR, cada merge se verifica automáticamente.

¿Qué es CI/CD?

CI (Continuous Integration) significa que cada vez que se envía código nuevo al repositorio, un servidor automáticamente lo compila, lo valida y ejecuta los tests. Si algo falla, el desarrollador recibe una notificación inmediata.

CD (Continuous Deployment) significa que cuando el código pasa todas las verificaciones, se despliega automáticamente a producción. No hay un paso manual de "subir al servidor" — todo es automático.

Workflow 1

CI — ci.yml

Se ejecuta en cada push a main y en cada Pull Request. Ejecuta 4 checks en secuencia sobre Ubuntu con Node 20 y caché de pnpm:

✓ tsc --noEmit — TypeScript compila sin errores (0 tolerancia)
✓ next lint — ESLint con reglas Next.js
✓ next build — Build completo de producción
✓ vitest run — 34 tests en 3 suites
Workflow 2

Security — security-review.yml

Se ejecuta en cada PR (eventos: opened, synchronize, reopened). Usa anthropics/claude-code-security-review@main, una acción oficial de Anthropic.

Claude Code analiza el diff completo del PR en busca de vulnerabilidades de seguridad y comenta directamente en el PR con sus hallazgos. Es como tener un auditor de seguridad revisando cada cambio automáticamente.

Workflow 3

Release — release.yml

Se ejecuta en cada push a main. Usa googleapis/release-please-action@v4.

Analiza los Conventional Commits (feat:, fix:, chore:, etc.) y genera automáticamente un PR de release con el CHANGELOG actualizado y un tag semántico de versión. Al mergearlo, se crea la release oficial en GitHub.

Sección 11

Infraestructura y Deploy

De un git push a producción en minutos. El pipeline está diseñado para que desplegar cambios sea tan seguro como escribir código.

El flujo completo en palabras simples

Cuando se hace un cambio en el código: 1) se crea un Pull Request en GitHub. 2) Automáticamente, 3 robots verifican el código: uno compila y testea, otro busca vulnerabilidades de seguridad, otro prepara la release. 3) Si todo pasa, se mergea. 4) Vercel detecta el cambio, recompila la app y la despliega en su red global de servidores. 5) En ~60 segundos, arkhos.pelayodelafuente.es está actualizado.

Pipeline: local → GitHub Actions → Vercel → producción global

Vercel — Hosting y CDN

Vercel es la plataforma de hosting conectada directamente a GitHub. Cada merge a main trigger un build automático de Next.js en los servidores de Vercel. El resultado se distribuye en su Edge Network global: servidores en decenas de países que sirven la app desde el nodo más cercano al usuario.

Preview deploys: cada PR genera automáticamente un deploy de preview en una URL única. Esto permite revisar cambios visualmente antes de mergear, sin afectar producción.

Branch protection

La rama main está protegida: nadie puede hacer push directo. Todo cambio debe pasar por un Pull Request y los CI checks deben estar en verde antes de poder mergear.

¿Por qué, si solo hay un desarrollador? Protege contra commits accidentales que rompen el build. Garantiza que todo código pasa TypeScript + tests antes de llegar a producción. Y establece el hábito de trabajo disciplinado.

Dominio y SSL

arkhos.pelayodelafuente.es con registro CNAME en Hostinger DNS apuntando a Vercel. El certificado SSL (HTTPS) es automático via Let's Encrypt, renovado por Vercel sin intervención manual.

Variables de entorno (12)

Configuradas exclusivamente en Vercel Dashboard. Las NEXT_PUBLIC_* (Supabase URL, anon key, site URL) se exponen al browser. Los secretos (service role key, API keys de Anthropic, CoinGecko, Alpha Vantage, FRED, Upstash, Sentry) solo existen en el servidor.

Infraestructura pendiente

Sentry — Error tracking

Monitorización de errores en producción en tiempo real. Cuando algo falla para un usuario, Sentry captura el error con contexto completo (stack trace, navegador, estado de la app) y notifica inmediatamente. Aplazado desde Fase 0.

PWA Service Worker

Funcionamiento offline básico. La app ya tiene manifest.json y los iconos PWA configurados. Falta el Service Worker que cachee los assets estáticos y permita abrir la app sin conexión. Aplazado desde Fase 0.

Framer Motion

Transiciones fluidas entre módulos y micro-animaciones en la interfaz. Layout animations para cuando las cards cambian de posición (filtros, drag & drop). Aplazado desde Fase 1.

Web Push API

Notificaciones push para alertas del módulo Mercados. Cuando Bitcoin supere $100K o cuando tus acciones caigan un 5%, recibirás una notificación aunque no tengas la app abierta.

Visión a largo plazo

Arkhos como plataforma modular personal donde cada módulo resuelve un área concreta de la vida (trabajo, inversiones, patrimonio, gastos) y eventualmente los módulos se conectan entre sí para crear una visión unificada.

Ejemplo de conexión futura

El Módulo Patrimonio muestra el valor de tus inversiones. Para calcular el valor actual, consulta precios en tiempo real del Módulo Mercados. El dashboard home muestra un resumen unificado: proyectos activos del Módulo Proyectos + valor del portfolio del Módulo Patrimonio + gastos del mes del Módulo Gastos + alertas de mercado del Módulo Mercados. Todo en una sola pantalla.

La arquitectura ya está diseñada para este escenario: Zustand stores independientes por módulo (se pueden conectar sin acoplar), RLS que garantiza que cada módulo solo accede a los datos de su usuario, componentes UI reutilizables en todos los módulos, y un stack cognitivo que hace que añadir nuevos módulos sea un proceso sistemático y predecible.
